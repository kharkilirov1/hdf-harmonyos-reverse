=== 92. Круг 21: ОТЛОЖЕННЫЙ Start в отдельном потоке — похоже, снял дедлок! ===

Дата: 2026-10-28. Продолжение 91_bpayr2_codes.

═══════════════════════════════════════════════════════════════════════
1. ГИПОТЕЗА
═══════════════════════════════════════════════════════════════════════

Наша пещера в libsafwk вызывает SystemAbility::Start(401) СИНХРОННО из
хука AddSystemAbilityListener(8250). Если этот хук срабатывает внутри
Init()/OnStart-пути того же потока, Start реентерабельно входит в
BundleMgrService::OnStart -> Init() -> и виснет на локе/фьюче
(наблюдали futex-зависание + watchdog "Start to check 240000ms ago").

Решение: вызывать Start НЕ синхронно, а из отдельного потока с задержкой:
  cave: Publish(self) (как раньше) + pthread_create(tramp, self)
  tramp: usleep(2 c); Start(self)

═══════════════════════════════════════════════════════════════════════
2. РЕАЛИЗАЦИЯ
═══════════════════════════════════════════════════════════════════════

docs/cave_defer.s — пещера (192 байта):
  - сохраняет x0..x8, проверяет [x20+8]==401 && w19==8250,
  - Publish(x20, &sptr на стеке),
  - pthread_create(&tid=sp+72, NULL, tramp, x20),
  - восстанавливает регистры, возвращается в оригинальный хвост.
  - tramp: сохраняет callee-saved, usleep(2_000_000), Start(self), ret.
docs/patch_defer_start.py — патчер: находит .plt (pthread_create@plt=
  0x24770, usleep@plt=0x24360), пещеру в padding .text (VA 0xf1ac),
  патчит 0x1f1e0 -> b cave.

═══════════════════════════════════════════════════════════════════════
3. РЕЗУЛЬТАТ ПРОГОНА (900 c)
═══════════════════════════════════════════════════════════════════════

  insert SA:401 = 7
  ВСЕГО insert SA: = 138   (в прежних прогонах ~60!)
  watchdog "BundleMgrService::Start to check ...240000ms" = 0
     => Start() ЗАВЕРШИЛСЯ (раньше всегда висел и срабатывал watchdog).
  DB bmsdb_slave.db при извлечении: "database disk image is malformed"
     => BMS АКТИВНО ПИСАЛ в базу в момент снятия питания (признак
        реальной работы установки/записи).
  /data/app/el1/bundle/public = 9 (HSP) на момент снятия
  slassistant/launcher в консоли: 0 (установка HAP ещё не дошла)

═══════════════════════════════════════════════════════════════════════
4. ВЫВОД
═══════════════════════════════════════════════════════════════════════

Отложенный Start разрывает реентерабельный дедлок: BMS OnStart/Init
проходит дальше, Start завершается без watchdog, система публикует
гораздо больше SA (138 против ~60), BMS пишет в БД.

Это первый вариант, где Init НЕ виснет навсегда. Нужно:
  A. Прогнать дольше (1500-2500 c), чтобы HAP-установка (и launcher)
     успела завершиться.
  B. Аккуратно извлекать БД (учитывать -wal/-shm или делать
     `PRAGMA wal_checkpoint` нечем; лучше смотреть public-каталоги и
     повторный прогон).
  C. Проверить текстовый hilog на "OnBmsStarting"/"Install System app".
