=== 118. Круг 40 (финал): appfwk.ready установлен 23 раза, appspawn 28; логи теряются из-за отсутствия sync ===

Дата: 2026-10-29. Продолжение 117_appfwk_ready.

═══════════════════════════════════════════════════════════════════════
1. РЕШАЮЩИЙ ПРОГОН 2400 c (insert SA:401 = 12)
═══════════════════════════════════════════════════════════════════════

В консоли:
    bootevent.appfwk.ready       — SET, 23 раза
    bootevent.appspawn.started   — SET, 28 раз
    bootevent.launcher.ready     — только 1 раз, и это
                                   "unset_bootevent bootevent.launcher.ready"
                                   на 804 c.

=> Ability Manager Framework и appspawn РАБОТАЮТ, система продвинулась
   до шага "запустить лаунчер". Осталось: установить пакет лаунчера и
   запустить его ability, чтобы он выставил launcher.ready.

═══════════════════════════════════════════════════════════════════════
2. ПОЧЕМУ НЕ УВИДЕЛИ РЕЗУЛЬТАТ bmrun
═══════════════════════════════════════════════════════════════════════

В консоли видно, что задания выполнялись:
    [ 469.6] Execute command "mkdir  /data/diag 0777 root root" took 236 ms
    [ 580.7] Execute command "mkdir  /data/diag 0777 root root" took 1338 ms
    [  74.0] ServiceStart started info bmrun(pid 1789 uid 0)
и bmrun жил (already started на 287, 359, 469 c).

НО в образе /data/diag ОТСУТСТВУЕТ: "File not found by ext2_lookup".
Причина: QEMU убивается SIGTERM (timeout), гость не успевает
синхронизировать ФС, и недавно созданные файлы/каталоги теряются
(журнал ext4 не проигран). Это же объясняет, почему в одних прогонах
файлы /data/diag/*.log есть, а в других — нет.

═══════════════════════════════════════════════════════════════════════
3. ЧТО СДЕЛАТЬ
═══════════════════════════════════════════════════════════════════════

  A. Добавить `sync` в bmrun.sh: после каждой записи в лог и особенно
     после INSTALL_OK / aa start / aa dump — вызывать /system/bin/sync
     (или busybox sync), чтобы данные гарантированно попали на диск.
  B. Уменьшить бут до ~1200-1500 c, но с sync; run-kill через
     `pkill -TERM` помягче + пауза 10 c перед проверкой образа.
  C. Повторить решающий сценарий: цикл установки (timeout 25, 50 попыток),
     затем 60 циклов `aa start` каждые 30 c (appfwk.ready появляется
     к ~1500 c), с sync после каждого шага.
  D. Критерий: появление в консоли установки (а не unset)
     bootevent.launcher.ready, либо лог aa с rc=0 и успешным dump.
