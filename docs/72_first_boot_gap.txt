=== 72. Круг 4: BMS НЕ входит в "first boot" -> install_list HAP не сканируется ===

Дата: 2026-10-28. Продолжение 71_hap_gap.

═══════════════════════════════════════════════════════════════════════
1. ГЛАВНОЕ ОТКРЫТИЕ ЭТОГО КРУГА
═══════════════════════════════════════════════════════════════════════

В логах ЭМУЛЯТОРА, прямо перед установкой 75 бандлов:
  C01120/BMS: OnBmsStarting first boot        (22:34:14)

В НАШИХ логах (все прогоны, в т.ч. с ПОЛНОСТЬЮ ЧИСТЫМ /data — прогон
с hilog-снимками на 260/380 c) строки "OnBmsStarting first boot" НЕТ.
=> BMS не считает наш запуск "первым" и НЕ выполняет первичное
   сканирование /system/app (install_list), поэтому HAP-приложения
   (включая лаунчер) вообще не устанавливаются. Ставятся только HSP
   из app_service_fwk_install_list (это отдельный, не-first-boot путь).

Проверено также:
  - все 182 записи install_list.json имеют существующие каталоги
    в /system/app (missing: 0);
  - в libbms есть строка "only scan app_list.json on first startup" —
    первичное сканирование выполняется только на первом старте.

═══════════════════════════════════════════════════════════════════════
3. ПОЧЕМУ ЭТО ВАЖНО
═══════════════════════════════════════════════════════════════════════

Пока BMS не начнёт "first boot" сканирование, HAP-приложения
(в т.ч. com.huawei.hmos.slassistant) не будут ставиться этим путём —
значит ни launcher.ready, ни boot.completed не появятся.

Ключевой вопрос следующего раунда: как BMS определяет "первый запуск"
(какой файл/БД/параметр проверяет) и как заставить его считать наш
запуск первым.

Кандидаты (проверить в коде libbms / по состоянию /data на эмуляторе):
  - наличие/отсутствие preinstall-данных в RDB (preinstall_data_storage);
  - флаг в /data/service/el1/public/bms/bundle_manager_service (например
    файл-маркер или таблица bms_param);
  - проверка "версии системы" vs "версии данных" (upgrade != first boot);
  - параметр persist.bms.* (data.preload / version).
