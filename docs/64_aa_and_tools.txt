=== 64. Раунд 45: aa start/dump висят так же, как bm ===

Дата: 2026-10-27. Продолжение 63_launcher_db_inject.

ЦЕЛЬ РАУНДА: проверить, отдаёт ли BMS нашу инъекцию, и запустить
лаунчер напрямую через aa start (минуя авто-старт).

ПРОГОН (минимальный install_list, БД с записью лаунчера, 850 c):
  insert SA:401 = 2; bootevents 10; launcher=0; slassistant=0 в консоли.

Пробы (init-джобы):
  aa1.log  (480 c) aa start -b com.huawei.hmos.slassistant
                   -a SuperLauncherMainAbility   -> 0 байт
  aa2.log  (520 c) aa dump -a                       -> 0 байт
  qh2.log  (600 c) hilog                            -> 0 байт
  aa3.log  (700 c) повтор aa start                  -> файл не создан

Файлы aa1/aa2/qh2 созданы delayed_exec'ом (значит команды запускались),
но вывод пуст: aa и hilog НЕ отвечают (висят до конца прогона), как и bm.

СВОДКА ПО ИНСТРУМЕНТАМ:
  bm  (dump/install) — висит в большинстве окон (в единичных прогонах
                       отвечал: usage, "failed to install bundle")
  aa  (start/dump)   — висит
  hilog              — иногда даёт снимок (187 КБ, 1.17 МБ), иногда 0
  hidumper           — пусто

ВЫВОД: SA-процессы (AMS/BMSExt и др.) в наших прогонах не обслуживают
RPC стабильно; рабочим остаётся только samgr (insert SA:401).
Поэтому ни bm-установка, ни aa-запуск лаунчера не проходят.

СОСТОЯНИЕ:
  - БД BMS с записью лаунчера — в дереве образа (переживает перезагрузку).
  - libsafwk с пещерой публикации SA 401 — применено.
  - install_list.json минимальный (только SuperLauncher).
  - Остальные библиотеки — оригиналы.

ВАРИАНТЫ ДАЛЬШЕ (для следующего раунда):
  1. Стаб ядра для /dev/tc_ns_client (misc-устройство: ioctl->0):
     цель — чтобы teecd не падал с 255 и devicesSecurityProxy вернул
     хоть что-то; но без TA/provision вероятность успеха verify низкая.

  3. Зафиксировать барьер окончательно (уже есть docs/60,61) и закрыть.
