=== 48. BMS UNBLOCK: "insert SA:401" ДОСТИГНУТ (code-cave + host pointer) ===

Дата: 2026-10-27. Продолжение 47_bms_unblock.

═══════════════════════════════════════════════════════════════════════
ГЛАВНЫЙ РЕЗУЛЬТАТ
═══════════════════════════════════════════════════════════════════════

Code-cave инъекция в libsystem_ability_fwk.z.so РАБОТАЕТ:
    SAMGR: insert SA:401_39   (на ~529 c)
    SAMGR: insert SA:401_39   (повторно, т.к. слушатель вызывается 3 раза)
Критерий "insert SA:401 в логе samgr" — ВЫПОЛНЕН.
bootevent'ы при этом идут (6-10 за прогон), kernel panic — 0.

═══════════════════════════════════════════════════════════════════════
КАК ЭТО СДЕЛАНО
═══════════════════════════════════════════════════════════════════════

Статический анализ (шаг 1, детали в docs/47_bms_unblock.txt):
  - libbms (6.0.0.108 arm64) НЕ импортирует SystemAbility::Publish;
  - нормальные SA (libscreen_session_manager, libabilityms) импортируют
    и вызывают Publish;
  - BMS создаёт host (BundleMgrHostImpl, 208 байт) и кладёт указатель в
    поле своего объекта по смещению +0x178 (видно в libbms: 0x2ae72c
    add x20,x0,#0x178; 0x2ae7ec str x19,[x20]).

Патч (patch_libsafwk.py + cave_safwk.s):
  - libsystem_ability_fwk.z.so, VA 0x1f1e0
    (ldr w2,[x20,#8]) -> b 0xf1ac  (пещера в padding .text);
  - пещера:
        if ([x20+8] == 401) {
            x9 = [x20 + 0x178];          // host (BundleMgrHostImpl*)
            if (x9) {
                slot = x9;
                Publish(x20, &slot);     // 0x1f324 (тот же .so)
            }
        }
        ldr w2,[x20,#8]; mov w1,w19; b 0x1f1e8
    x20 = SystemAbility* (self), w19 = listener id.
  - конкретно байты патча: 82 0a 40 b9 -> f3 bf ff 17 (b 0xf1ac).

Проверка ABI: GetAbilityRemoteObject пишет sptr по x8 (sret) —
первая версия пещеры (без x8) ломала OnStart; от неё отказались,
используем host-поле +0x178 (Publish сам делает IncStrongRef).

═══════════════════════════════════════════════════════════════════════
ЧТО ПОКА НЕ РАБОТАЕТ
═══════════════════════════════════════════════════════════════════════

bm CLI после публикации всё ещё недоступен:
  - "bm dump -n com.huawei.hms.weather" иногда -> "error: failed to
    execute your command.", иногда пустой вывод;
  - "bm install -p .../SuperLauncher.hap" -> пустой вывод;
  - лаунчер в /data/app/el1/bundle/public НЕ появился;
  - bms.main.bundles.ready / launcher.ready отсутствуют.

Гипотезы:
  1. Публикация трижды (на каждый AddSystemAbilityListener) может ломать
     состояние samgr/объекта — нужен флаг "опубликовать один раз".
  2. RPC к BMS может виснуть (bm печатает пусто = вероятно, ждёт ответа
     и убивается при рестарте init-джоба).
  3. Хост мог быть опубликован до полной инициализации BMS — порядок
     вызова слушателей и создания host надо уточнить.

═══════════════════════════════════════════════════════════════════════
СЛЕДУЮЩИЕ ШАГИ
═══════════════════════════════════════════════════════════════════════

1. Добавить в пещеру флаг "published" (в свободной writable памяти .data
   .so) — публиковать только один раз, при первом вызове listener.
2. Проверить, доходит ли bm RPC до BMS (kernel binder tracing по 401->
   foundation), и не виснет ли обработчик (OnRemoteRequest host).
3. Если виснет — публиковать не host, а создать/дождаться полной
   готовности BMS (например, публиковать на 3-м слушателе 8250 или по
   таймеру из init-джоба).
