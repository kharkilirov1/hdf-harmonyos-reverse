=== 50. Раунд 31: bm падает на создании command map; toybox без sh ===

Дата: 2026-10-27. Продолжение 49_bms_rpc.

═══════════════════════════════════════════════════════════════════════
1. ПОЧЕМУ У bm «failed to execute your command»
═══════════════════════════════════════════════════════════════════════

Строки bm рядом с этой ошибкой (файл /system/bin/bm, offset 0x3bef):
    "failed to create message map."
    "failed to create command map."
    "failed to execute your command."
=> "error: failed to execute your command." — это НЕ неверные аргументы,
   а следствие того, что bm не смог построить command map.
   Command map строится при старте и, судя по поведению, требует
   рабочего прокси BMS (SA 401): если прокси нет — карта пуста и любая
   команда даёт эту ошибку.
   Это согласуется с более ранними прогонами: "bm dump -n ..." ->
   error; в других прогонах вывод пуст (ошибка уходила в HiLog, который
   нам недоступен).

2. ПОЧЕМУ ПУСТЫЕ ФАЙЛЫ У SHELL-ОБЁРНУТЫХ ПРОБ
═══════════════════════════════════════════════════════════════════════

Найденная причина: в этом образе toybox собран БЕЗ апплета sh:
    toybox: Unknown command sh
Поэтому все попытки "toybox sh -c ..." и скрипты с shebang
"#!/system/bin/toybox sh" не выполнялись (файл лога создавался
перенаправлением, но команда не запускалась).

3. WAIT_EXEC
═══════════════════════════════════════════════════════════════════════

wait_exec (раннер с RC/TIMEOUT) создаёт файл, дочерний процесс
запускается, но строка [RC=...] в файл не попадает — предположительно
из-за особенностей namespace/буферизации у init-джобов. Вывод диагностики
нужно писать не в тот же файл, а в консоль (stderr) и в отдельный файл.

4. СОСТОЯНИЕ ПУБЛИКАЦИИ
═══════════════════════════════════════════════════════════════════════

- Рабочая пещера восстановлена: insert SA:401 = 3 (в прогоне с
  приглушёнными kernel-логами), bootevents 5.
- Прогон до этого (с шумными FNDTXN/SAMGRADD) сильно тормозил:
  foundation стартовал в 142 c и повторно в 608 c, insert не успевал.
  FNDTXN/SAMGRADD приглушены (печатают 1 раз).

СЛЕДУЮЩИЕ ШАГИ (раунд 32)
═══════════════════════════════════════════════════════════════════════

1. Сделать bmrun: обёртка, которая запускает bm, ждёт с таймаутом и
   печатает статус в stderr (консоль) + отдельный файл. Так мы точно
   узнаем, падает bm мгновенно или висит.
2. Проверить, возвращает ли samgr GetSystemAbility(401) не-null:
   написать минимальный статический клиент (libipc через dlopen) или
   использовать hidumper/dumpsys, если есть.
3. Если GetSystemAbility(401) возвращает null — значит наша публикация
   не даёт рабочий handle: разобраться, что делает штатный Publish
   (какой объект маршалится) и сравнить с нашим вызовом.
