=== 88. Круг 18: корреляция запрос->ответ; ATM id 3503; гипотеза SA 5 ===

Дата: 2026-10-28. Продолжение 86_bpayr_replies.

═══════════════════════════════════════════════════════════════════════
1. CORR: попытка корреляции по debug_id
═══════════════════════════════════════════════════════════════════════

Добавлены: BPAY id=<t->debug_id>, BPAYR req=<thread->transaction_stack->
debug_id. Результат: все ответы печатают req=0 — в момент
binder_transaction(reply=true) thread->transaction_stack уже пуст.
Корреляция по debug_id не работает без правки в binder_thread_write
(печатать исходный id до обработки BC_REPLY).

Дополнительно в BPAY добавлен from=<pid> — это сработало.

Отправители запросов к samgr (топ):
  from=3003 bootanimation code=2 x985
  from=1811 cadaemon code=12 x779
  from=1879 dlp_credential code=2 x729
  from=2026 wallpaper code=12 x708
  from=2005 netmanager code=12 x536
  from=2444 foundation code=12 x467
  from=1914 multimodalinput code=2 x461
  from=2021 telephony code=12 x420
  from=1869 audio_server code=12 x418
  from=2095 msdp code=2 x418
  ...

Парсинг payload: Parcel = [0x00000100][0][len][UTF-16 строка интерфейса].
Строка = "ohos.samgr.accessToken" (len=0x16=22) — это дескриптор
AccessTokenManager; клиенты массово запрашивают именно его.

Ответы samgr -> foundation: first=00000007 x1236 (ERROR 7) — от 334 до
770 c, ~2/с, не прекращаются.

═══════════════════════════════════════════════════════════════════════
2. ATM ID: 3503, а не 5
═══════════════════════════════════════════════════════════════════════

/system/profile/accesstoken_service.json:
  { "name": 3503, "libpath": "libaccesstoken_manager_service.z.so",
    "run-on-create": true }
В логе: insert SA:3503 в ~233-310 c. SA с id 5 НЕ публикуется.
Клиенты же (судя по дескриптору "ohos.samgr.accessToken") массово
получают ERROR 7 — вероятно, часть клиентов ищет ATM по id 5 (или по
дескриптору, который не совпадает), и это создаёт постоянный фон
неудач.

═══════════════════════════════════════════════════════════════════════
3. ЭКСПЕРИМЕНТ: опубликовать ATM как SA 5 — НЕУДАЧА
═══════════════════════════════════════════════════════════════════════

Пробовали:
  (a) добавить второй entry {name:5, ...} к 3503 -> публикуется только
      3503, SA:5 не появляется (sa_main берёт первый/не разрешает дубль);
  (b) заменить 3503 на 5 -> ATM вообще не публикуется (ни 5, ни 3503),
      error7 вырос до 2600, BMS не создал даже таблиц (DBERR).

Вывод: id 5 для этой сборки/reserved-конфликт — так делать нельзя.
Профиль ВОЗВРАЩЁН к исходному {name:3503}.

═══════════════════════════════════════════════════════════════════════
4. ПЛАН
═══════════════════════════════════════════════════════════════════════

  A. Не трогать id ATM. Вместо этого выяснить, какие именно запросы
     foundation получают ERROR 7: сделать корреляцию в binder_thread_write
     для BC_REPLY (печатать id запроса из thread->transaction_stack до
     его обнуления), связать с BPAY-payload (дескриптор/id).
  B. Если выяснится, что foundation циклится на ATM-дескрипторе из-за
     несовпадения id -> патчить libbms (или профиль ATM), чтобы запрос
     резолвился.
  C. Параллельно: вернуть/проверить ранний старт ATM (он остался) и
     смотреть, не появится ли продвижение Init в новых прогонах.
