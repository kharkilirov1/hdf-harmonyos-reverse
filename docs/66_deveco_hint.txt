2. ГЛАВНАЯ ПОДСКАЗКА: У ЭМУЛЯТОРА НЕТ TEE/HKS ВООБЩЕ
═══════════════════════════════════════════════════════════════════════

В образе эмулятора (6.0.1 wearable x86_64) НЕТ:
  /system/bin/teecd, /system/bin/hks_compatibility_bin, libhks/tee-библиотек.
Ядро эмулятора — x86 5.10.210, строк tc_ns/tzdriver/tee в нём НЕТ.
=> Эмулятор работает без TEE/HKS. Значит у BMS есть штатный
   "эмуляторный" путь, при котором подпись не проверяется.

В обоих libbms (наш arm64 6.0.0.108 И эмуляторный x86) есть строка:
  "%{public}s:%{public}s:%{public}d Emulator does not verify signature"
и символ BmsExtensionDataMgr::IsRdDevice.

3. ЖИВЫЕ ПАРАМЕТРЫ ЭМУЛЯТОРА (через hdc)
═══════════════════════════════════════════════════════════════════════

  const.product.model            = emulator
  const.product.name             = emulator
  const.product.software.version = "emulator 7.0.0.107(SP8DEVC00E999R4P11)"
  const.product.brand            = HUAWEI
  const.build.characteristics    = default
  const.product.devicetype       = phone

В НАШЕМ arm64-образе было:
  const.product.model=ohos
  const.product.name="OpenHarmony 3.2"
  const.product.software.version=OpenHarmony 6.0.0.107

libbms читает именно const.product.name (строка есть в libbms).
ВЫВОД: BMS, скорее всего, определяет эмулятор по
const.product.name == "emulator" (и/или model/software.version)
и тогда пропускает проверку подписи.

     (trusted_root_ca, trusted_source_manager работают!)
  При этом установка части system-бандлов ВСЁ РАВНО падает:
     install system bundle fail error: 8519714 / 8519686 / 8519891
  НО эмулятор всё равно загружается до UI (SYS_UI, sceneboard),

  лаунчер (com.ohos.sceneboard и др.) — их не надо ставить.

=> Второй вывод: можно не устанавливать лаунчер, а принести его
   "уже установленным" в /data (как в userdata эмулятора):
   /data/app/el1/bundle/public/<bundle>/... + записи BMS DB.

5. ЧТО СДЕЛАНО В ЭТОМ РАУНДЕ (проверка гипотезы)
═══════════════════════════════════════════════════════════════════════

В /system/etc/param/ohos.para нашего arm64-образа выставлено:
  const.product.model=emulator
  const.product.name=emulator
  const.product.software.version="emulator 6.0.0.108"
(бэкап: ohos.para.orig.hm)

Первый прогон вышел медленным: сработал "first-boot/installer" путь
(param_service/install, mkdir /mnt/sys_installer и т.п.), к 730 c
foundation только стартовал, insert SA:401 ещё не дошёл.
Причина, вероятно, некорректная строка с пробелом без кавычек
(исправлено на "emulator 6.0.0.108").

═══════════════════════════════════════════════════════════════════════
6. ПЛАН ПРОВЕРКИ
═══════════════════════════════════════════════════════════════════════

1. Перезапуск с исправленным ohos.para (кавычки), 900-1200 c:
   ждать insert SA:401, bms.main.bundles.ready, установку лаунчера.
2. Если BMS реально пошёл в "Emulator does not verify signature" —
   проверить по БД (installed_bundle += com.huawei.hmos.slassistant)
   и по логу hilog (снимок ловит строку Emulator does not verify).
3. Если параметра недостаточно — найти статически ветку в arm64
   libbms (функция, читающая const.product.name) и принудительно
   включить эмуляторный режим патчем (mov w0,#1 / b <skip verify>).
4. Параллельно: вытащить userdata.qcow2 эмулятора (Mate 90 Pro),
   посмотреть раскладку /data для лаунчера (bundle_info.json и т.п.)
   и воспроизвести её в arm64-образе — путь "уже установлен".
